# 部署与打包说明

本文说明两件事：Web 两件套（React 管理端 + Go 后端）怎么用 Docker Compose 一键跑起来，Unity 客户端怎么打包成可分发的 exe。

需求本身只规定「SQLite 或本地 JSON 文件、不引入外部数据库服务」，编排方式与打包产物属于实现选择，因此本文不是需求基线的一部分；功能与接口契约仍以[需求规格说明书](需求规格说明书.md)为准。

## 1 组成

| 服务 | 镜像 | 对外端口 | 说明 |
| --- | --- | --- | --- |
| `frontend` | `unity-3d-inspection/frontend` | `${FRONTEND_PORT:-8088}` → 80 | Nginx 托管 `dist/`，`/api` 反代到 `backend:8080` |
| `backend` | `unity-3d-inspection/backend` | `${BACKEND_PORT:-8080}` → 8080 | Go 静态二进制，数据在命名卷 `/data` |

浏览器只访问前端端口，与后端同源，不触发跨域；Unity 客户端是原生程序，直接连后端端口，不受同源策略约束。

## 2 一键运行

```cmd
start-docker.cmd            :: 构建（镜像缺失时）+ 启动 + 等健康 + 打开浏览器 + 拉起 exe（若已构建）
start-docker.cmd web        :: 同上但不拉起 Unity 客户端
start-docker.cmd build      :: 强制重建镜像后启动
start-docker.cmd down       :: 停止（数据卷保留）
start-docker.cmd logs       :: 跟踪日志
start-docker.cmd check      :: 环境自检
```

等价的 compose 命令：

```bash
docker compose up -d --build
docker compose ps
docker compose logs -f
docker compose down          # 数据卷保留
docker compose down -v       # 连数据一起删除
```

脚本的核心逻辑在 `Tools/start-inspection.ps1`：`docker` 动作先校验 Docker 与 Compose、引擎状态，再 `up -d`，然后轮询 `http://localhost:8088/` 与 `http://localhost:8080/api/health` 直到就绪（最多 60 秒），最后打开浏览器。失败按约定返回码：依赖缺失 2，运行失败 1。

## 3 参数

根目录 `.env.example` 列出了全部可覆盖项，复制成 `.env` 即可生效（`.env` 已被忽略，不会入库）。不建 `.env` 时 compose 里的默认值直接可用。

| 变量 | 默认值 | 说明 |
| --- | --- | --- |
| `FRONTEND_PORT` | `8088` | 管理端对外端口 |
| `BACKEND_PORT` | `8080` | 后端对外端口，Unity 客户端连的就是它 |
| `TAG` | `latest` | 镜像标签 |
| `BASE_REGISTRY` | `docker.m.daocloud.io/library/` | 基础镜像前缀；直连 Docker Hub 时设为空 |
| `GOPROXY` | `https://goproxy.cn,direct` | 构建期 Go 模块源 |
| `NPM_REGISTRY` | `https://registry.npmmirror.com` | 构建期 npm 源 |

`BASE_REGISTRY` 用的是 `${BASE_REGISTRY-default}` 形式：**未设置**时取默认加速站，**显式设为空**时走 Docker Hub。这样同一份 `compose.yaml` 在能直连与不能直连的环境都能用。

## 4 数据

- 容器数据在命名卷 `unity-3d-inspection-data` 的 `/data/issues.db`（SQLite，WAL 模式），另有两个伴生文件 `issues.db-wal` / `issues.db-shm`。
- 宿主机 `go run ./cmd/server` 用的是 `backend/data/issues.db`，与卷里的那份**互不影响**。
- 备份：`docker run --rm -v unity-3d-inspection-data:/data -v %cd%:/backup alpine tar czf /backup/inspection-data.tar.gz -C /data .`
- 清除：`docker compose down -v`。

## 5 旧 JSON 数据迁移

旧版本把问题存在 `backend/data/issues.json`。现在统一用 SQLite，迁移是显式动作、可重复执行（同一「标识 + 创建时间」会跳过）：

```bash
# 宿主机（本地 go run 场景）
cd backend
go run ./cmd/migrate -from data/issues.json -to data/issues.db
```

容器场景要把文件送进卷再迁移：

```bash
docker compose cp backend/data/issues.json backend:/data/
docker compose exec backend /usr/local/bin/migrate -from /data/issues.json -to /data/issues.db
docker compose exec backend rm /data/issues.json      # 确认导入无误后可删
```

迁移不参与服务启动，避免"容器一爬起来就悄悄改了数据"这种难排查的行为。

## 6 Unity 客户端打包

Unity 构建必须在本机 Windows 上用已激活的编辑器完成，Linux 容器里做不了；GUI 程序也无法在容器中运行。所以 exe 不进编排，由 `start-unity.cmd` 负责构建与打包。

```cmd
start-unity.cmd             :: 源码有变化时构建，然后运行 unity\Build\UnityInspection.exe
start-unity.cmd build       :: 强制重新构建再运行
start-unity.cmd package     :: 构建 + 汇总 + 压缩成 release\UnityInspection-win64.zip
start-unity.cmd editor      :: 打开编辑器手动调试
```

`package` 产出：

```
release/
├── UnityInspection-win64/          # 可直接运行的目录
│   ├── UnityInspection.exe
│   ├── UnityInspection_Data/
│   ├── UnityPlayer.dll
│   ├── UnityCrashHandler64.exe
│   └── backend-config.json         # 后端地址配置
└── UnityInspection-win64.zip       # 分发用压缩包
```

`release/` 已加入 `.gitignore`。

### 后端地址

exe 默认连 `http://localhost:8080`。要指向别的机器，改同目录的 `backend-config.json`：

```json
{
  "baseUrl": "http://192.168.1.20:8080"
}
```

规则：只认 `http://` 或 `https://` 开头的地址；文件缺失、JSON 非法或前缀不对时忽略并保留默认值；末尾的 `/` 会被去掉。启动日志会打印实际使用的地址，便于现场核对。

## 7 改动后的自查

```bash
# 后端
cd backend
go vet ./...
go test ./...          # 特征化测试 + 存储一致性套件必须全绿
go build ./...

# 前端
cd frontend
npm run build          # tsc --noEmit + vite build

# 编排
docker compose config  # 校验 compose.yaml 与变量替换
docker compose up -d --build && docker compose ps
```

冒烟：管理端能列出问题、Unity 能上报、`PATCH` 改状态后两端一致。
